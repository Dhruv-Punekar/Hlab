1. CONTROLS
  P1, near end, red racket   : BTNR forehand   BTNL backhand
  P2, far end, black racket  : BTNU forehand   BTND backhand
  The server serves with either of his two buttons, the receiver returns
  with either. Forehand / backhand only choose the swing animation.
  BTNC        short press: next camera view (player 1 / side / player 2)
              hold 1 s: new game (score 0-0, the other player serves first)
  CPU_RESETN  full reset (P1 serves first, view player 1)
  SW0 = 1     P2 played by the computer      SW1 = 1   P1 by the computer
              (both on: demo mode; the computer misses 1 ball in 8)
  SW2 = 1     P1 tilt aiming (see 7.)        SW3 = 1   mute
  SW4 = 1     invert the tilt direction      SW5 = 1   use accelerometer Y
  LEDs        LD0..3 buttons, LD4..11 aim position (SW2 on) or camera view,
              LD12 / LD13 P1 / P2 serves, LD14 game over,
              LD15 render overrun (must stay off, see 5.)


2. GAME RULES (simplified ITTF)
  - Serve: the ball bobs in front of the server's racket until he presses.
    It bounces once on the server's half, then once on the receiver's half.
  - Return: the ball bounces once on the opponent's half.
  - A return counts only if the button is pressed in the HIT WINDOW:
    3 .. 16 frames (50 .. 267 ms) before the ball reaches the racket,
    and only if the racket is within reach: |racket base x - ball x| <=
    0.16 m (racket bases slide 1 cm per frame, limited to +-0.45 m).
    The swing then meets the ball (contact = 8 frames after the press, i.e.
    between 133 ms before and 83 ms after the ball arrives) and the ball goes
    back. Pressed too early, too late or not at all: the ball flies past
    the racket, disappears and the point goes to the other player.
  - Serve changes every 2 points.
  - The first player to 11 points wins the game (no deuce). At game over
    the winner's score blinks; BTNC held 1 s starts the next game.
  - Without tilt aiming the ball stays close to the middle line (bounce x
    within +-12 cm).
  All numbers are constants in tt_game_model.py (HIT_EARLY, HIT_LATE, arc
  frames and heights, ...), regenerated into tt_game_map.vh.

  Ball flight per shot: rally 30 frames to the bounce + 22 frames to the
  racket = 0.87 s; serve 14 + 26 + 22 frames. Arcs are integer physics
  (p += v, vy -= g per frame, Q16.16) aimed exactly at the bounce points;
  the rally arc clears the net by ~15 cm, the serve by ~4.5 cm.

  Swing animation: 24 frames (rest, back-swing, contact at frame 8,
  follow-through, rest), racket moved and turned about the vertical axis.
  Forehand on the player's right, backhand on his left. Idle rackets slide
  sideways towards the incoming ball. The ball spins in flight.


3. ARCHITECTURE

  pixel clock 25.175 MHz                  render clock 100 MHz
  tt_buttons  -> press events             render sequencer (tt_game.v)
  tt_game_core  step at line 440 --pose bus + toggle-->  capture poses
                (~30 clocks)                              rst_render_n = 0
  tt_score_overlay <- pipeline VGA out                    tt_obj_animator:
     score panel, line 440 / 40 ticks                     156 vertices, 1.6 us
                                                          rst_render_n = 1:
                                                          clear + render

  - Moving objects: their vertices are stored last in vertices.mem (843 ..
    998). Each frame the animator writes them again from the object ROM
    (local coordinates) and the poses: X = tx + (cos lx + sin lz) >> 14,
    Y = ty + ly, Z = tz + (cos lz - sin lx) >> 14. A hidden ball has all
    vertices on one point (zero-area triangles are discarded by setup).
  - hardware_pipeline: new parameter VTX_WRITE_EN and ports vtx_we /
    vtx_addr / vtx_data (write while rst_render_n = 0). Default 0: the ports
    are ignored and can stay unconnected; cube and picture demos render
    bit-identically (checked).
  - Score: drawn on the VGA output stream, not rendered, so it costs no
    render time and cannot flicker. Panel at screen (398, 46), 66 x 26 px,
    top-right of the picture; P1 red, P2 white, yellow bar under the server.


4. TIMING / SLACK (design rules followed)
  Render clock, 10 ns:
  - Animator: 6 register stages, one operation each: distributed ROM read,
    3:1 pose mux, 16x16 multiplies (DSP48 with input + output registers),
    33-bit sum, 20-bit add, write registers. 4 DSP48E1.
  - Vertex memory: one 2:1 LUT in front of the BRAM address (write port or
    fetch address); write data straight from registers.
  - Sequencer: small FSM.
  Pixel clock, 39.7 ns:
  - All game logic runs here: a step is a sequence of ~30 micro-steps, one
    clock each, so no long combinational chains; the only multiplier (launch
    velocity, 33 x 17 bit) has registered inputs and output.
  - Overlay: 2 register stages (position decode, glyph + colour mux).
  Clock-domain crossings: see tt_game.v header; set_clock_groups
  -asynchronous between the two MMCM clocks, false paths on buttons /
  switches / reset / LED / VGA ports (constraints.xdc).
  Vivado check after implementation: report_timing_summary (WNS >= 0 on
  both clocks) and report_cdc (the pose bus is a CE-controlled crossing).


5. FRAME TIMING (no tearing)
  The framebuffer is read on VGA lines 40 .. 439. At line 440 the game
  steps and requests a render: animator 1.6 us + clear 1.2 ms + render
  ~1.9 ms = ~3.1 ms, inside the 3.97 ms until line 40 (~0.85 ms spare,
  worst case over all game poses from the model). LED15 latches if a
  render is ever still running at line 40.
  Resources added: no BRAM (vertex count unchanged, 999), ~6 DSP48, a few
  hundred LUT/FF.

7. STEP 3: CAMERA VIEWS, SOUND, TILT AIMING

  Camera views (BTNC short press cycles them)
    0 player 1  camera behind P1 (the original view)
    1 side      camera at the side of the table, 6.8 m out
    2 player 2  camera behind P2
    All three use the same pitch and FOV, so the horizon is on the same row
    (114) and the sky / floor clear split is unchanged. There is no clipper,
    so each view has its own static scene (floor grid and pruning made for
    its camera): gen_tt_scene.py writes them all to tt_views.mem
    (3 x 1173 lines of {X, Y, Z, RGB565}, Q8.8) and the matrices to
    tt_view_mat() in tt_scene_map.vh.
    Each frame, while the render domain is held in reset, tt_view_loader
    copies the selected view (static vertices 0 .. 1172 + 16 matrix words,
    ~12 us), then tt_obj_animator writes the rackets and the ball after it
    (1173 .. 1328). VERTEX_DEPTH is 2048; the view ROM is ~6 RAMB36.
    Render time, worst case over all game poses: 3.12 / 2.41 / 2.62 ms
    (gap 3.97 ms). Previews: preview.png, preview_view1.png, preview_view2.png.

  Sound (tt_sound.v, pixel clock, no BRAM)
    hit 1.3 kHz tock + noise click, bounce 820 Hz, point 523 Hz longer tone;
    sine table + exponential envelope, 49.2 kHz samples, 8-bit PWM on
    AUD_PWM (driven low or released, as Digilent specifies), AUD_SD = amp on.
    Events come from tt_game_core (snd_hit / snd_bounce / snd_point).
    SW3 mutes.

  Tilt aiming (SW2, P1 only)
    adxl362_reader (hardware_pipeline/game_files, clocked at 25.175 MHz:
    ~1 MHz SPI, 100 samples/s) -> tt_tilt: low-pass, dead zone +-50 mg,
    clamp +-400 mg, scaled to an aim x of up to +-0.39 m (TT_TILT_MAX).
    With SW2 on:
    - P1's serves and returns bounce at the aimed x on P2's half; the ball
      keeps travelling sideways, so it reaches P2 at x + (x - P1 x) * 5/16.
    - P1's racket follows the ball 4 cm per frame, so it is always there;
      P1 only chooses the moment (button, or automatic with SW1 on).
      SW1 + SW2: P1 fully automatic, direction by tilting the board.
    - P2's racket (1 cm per frame, reach 0.16 m) can miss wide balls, so
      aiming wins points.
    LD4..11 show the aim position (LD11 = far left).
